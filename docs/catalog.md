# Repository catalog

One map of what this repository ships, what it generates, and what belongs to
the instance. Paths are repo-relative; `~` is the current user's home. This is
an index, not a mechanism — no script reads it, so no path moved.

## Top level

| Path | Kind | Owner | Committed | Written by | Read by |
|---|---|---|---|---|---|
| `install.ps1` | source | toolkit | yes | maintainer | user, once |
| `scripts/` | source | toolkit | yes | maintainer | digest, closeout, checks |
| `config/` | source + template | toolkit | yes | maintainer | `install.ps1`, launcher |
| `docs/` | source | toolkit | yes | maintainer | agent, user |
| `plugins/tool-snapshot/` | source | toolkit | yes | maintainer | OpenCode daemon |
| `registries/` | mixed | toolkit + machine | partly | scanner + plugin | scanner, `tools_now.py` |
| `templates/` | seed | toolkit | yes | maintainer | `install.ps1` |
| `workspace/` | instance | user | no | agent, checks | session digest |
| `README.md`, `AGENTS.md`, `CHANGELOG.md`, `SECURITY.md`, `LICENSE` | source | toolkit | yes | maintainer | user, agent |

`workspace/` is the instance. It is git-ignored and may contain customer data.
`ABAP_WORKSPACE` can point it elsewhere; `scripts/_paths.py` resolves the path.

## Registries — two categories

Baseline: committed, stable, updated only when the machine's installed assets
change. Written by `registry_check.py --init` / `--refresh`.

| File | Holds |
|---|---|
| `skills.json` | every installed `SKILL.md`, with harness, owner, hash, status |
| `agents.json` | every agent, with owner, editable flag, declared skills |
| `mcp-servers.json` | configured MCP servers, enabled state, command kind, URL host |
| `tools.json` | baseline of the live tool catalog: total, namespaces, tool IDs |

Live: generated by the plugin, git-ignored because it carries local paths and
destination names. Written by `plugins/tool-snapshot/`.

| File | Holds |
|---|---|
| `tools-snapshot.json` | latest catalog summary; compared with `tools.json` |
| `tools-full.json` | latest full tool list (`id`, `name`, `namespace`, `description`) |

The check report is not a registry. It is written to
`workspace/memory/reports/registry-report.md` by `registry_check.py --check`.

## Scripts — flat by design

Eight small files; names state the job. No subfolders — one import path
(`_paths.py`) and one call per check. Keep new checks at this level.

## Registration contract — shared by both register skills

The two skills `sap-project-register` and `sap-program-register` use this contract.
Keep the rules here, not duplicated in both skill files. Both skills ask the user
at invocation; neither invents a value and neither deploys or connects to SAP.

Required inputs — a blank is a blocker, not a default:

- Project: code (short uppercase), SID/description, ADT URL, SAP Logon destination,
  SAP user, language, TLS CA path, allowed packages, test client. No TR — no
  program or SAP object exists at project registration. No owner input.
- Program: name (SAP object name), one-line purpose, FS path or explicit "none",
  knowledge domains, and explicit permission to write outside the current program.
- Permission to create `Projects/<PROJECT>/`, edit the portfolio `INDEX.md`, and
  edit `~/.config/opencode/opencode.json` and `~/.config/opencode/sap/profiles.json`.

Question mode — how both skills must ask:

- **Default: sequential.** Ask one question at a time with the `question` tool,
  using options when the answer is a choice. Never post a multi-row form and ask
  the user to fill it in one go. Batch answers only when the user explicitly asks
  for it (e.g. "ตอบทีเดียว" / "answer all at once").
- **Reuse context first.** Before asking, restate what is already known — project
  code, client, user, engines, FS status. Ask only for the missing values. Never
  re-ask a value the user already supplied in this session.
- **Validate each answer before the next question.** Check it against the gates
  below (folder exists, domain resolves, permission granted, FS present/absent).
  Stop immediately on a blocker; do not collect the rest of the form.
- **Order by dependency.** Project code → client → profile name; FS status → FS
  path; permission → any write outside the current program. Skip branches that do
  not apply (e.g. no FS → no FS path question).
- **Match the user's language.** Stay in the language the user writes in; do not
  mix languages in one prompt.

Object lookup — program registration only:

- Once an object name is known, do a **read-only** lookup on the project's system
  before asking for package or TR. Run `python scripts\tools_now.py`, confirm the
  system/client, and use that project's live `arc1-*` engine:
  `SAPSearch(searchType="tadir_lookup", names, objectTypes)` for existence and
  package, then `SAPTransport(action="list"/"get")` for the TR holding it. Never
  enable a server or write to SAP during registration.
- **Found:** report the package. If a TR can be confirmed, record it. If no TR is
  found or the result is inconclusive, ask the user for the number — never guess.
- **Not found:** treat as new — ask package and TR (no TR question when the package
  is `$TMP`).
- **Lookup failed, no logon, engine unavailable, or result unclear:** stop and ask
  the user. Never claim "not created" from a failed or empty search (see
  `working-method.md` §"Verify before claiming absence").

Gates:

- `sap-project-register` owns the project folder, `project.yaml` (including
  `allowed_packages` and `transport: none`), project README/AGENTS, `_archive`/
  `_sandbox`, the **project row** in portfolio `INDEX.md`, and optional disabled
  MCP profile. It never creates a program folder or asks for a TR.
- `sap-program-register` requires the project folder to exist. It owns the program
  folder, `program.yaml`, `spec.md`, `CHANGELOG.md`, `spec/source/`,
  `reports/DECISIONS.md`, the memory card, the **program row** in portfolio
  `INDEX.md`, and the entry in the project `README.md` §Programs. It never touches
  MCP config or another program's row.
- Transport is **program-level and optional**. Read `allowed_packages` from
  `project.yaml`: if it is `$TMP` only, do not ask for a TR number at all. Otherwise
  ask whether a TR exists and accept "not yet" — never invent one. Record the answer
  in `program.yaml` `transport:` and the program `AGENTS.md` §Deploy.
- If `allowed_packages` is missing or empty (an older scaffold), ask the user for it
  with one `question` call and use the answer for this program only. Do **not** edit
  the project's `project.yaml` — that belongs to `sap-project-register`. Record the
  answered value and its source ("user supplied at program registration") in
  `reports/DECISIONS.md`.
- `memory_check.py` checks every card stem under `memory/projects/<project>/*.md`
  against `INDEX.md`. A program card without its own INDEX row is a warning, so
  keep the two INDEX writes strictly per-owner.
- No FS → draft spec using the `HCL_INTERFACE_QA32` pattern; open questions are
  the scope. With FS → copy to `spec/source/` as immutable; a new FS is a new file
  plus a new `fs_version`.
- Never ask the user to paste a password. The user stores it himself with
  `store-sap-secret.ps1 -Profile <profile>`.
- Stop if any required answer is blank, a file would be overwritten, a domain
  name does not resolve, or permission for an outside folder is missing.

## Unregistration contract — shared by both unregister skills

The two skills `sap-project-unregister` and `sap-program-unregister` use this
contract. They undo only what the matching register skill created. They never
touch SAP objects, transports, stored credentials, or another project/program.

**Confirm every time — no inherited approval:**

- Resolve the exact, case-sensitive name; reject path separators, `..` and
  wildcards. If the folder or manifest is missing, report and stop — never claim
  success for removing nothing.
- Build and show the removal set before asking: folder path + file count, INDEX
  row, README line, memory card / spec mirror, and any MCP entries. State what
  will remain (SAP object, TR, other programs, stored credential).
- **Q1 — mode:** one `question` call with two options: `A` move to local
  `_archive`, `B` hard delete. No hidden default. For `B`, say in a full sentence
  before Q2 that deletion is permanent and cannot be undone.
- **Q2 — final confirm:** one `question` call restating target, chosen mode and
  removal set. Options `confirm` / `cancel`; default `cancel`. Execute only after
  `confirm`. Cancel at either question → stop and change nothing.
- Repeat Q1 and Q2 on **every** invocation, even if a previous turn said "delete
  it". An interrupted run restarts from Q1.

Gates:

- `sap-program-unregister` owns the program folder, `program.yaml`, `spec.md`,
  `CHANGELOG.md`, `spec/source/`, `reports/`, the memory card, the program row in
  portfolio `INDEX.md`, the project README §Programs line, and the spec mirror.
  It never touches MCP config or another program.
- `sap-project-unregister` owns the project folder, the project row in portfolio
  `INDEX.md`, and the MCP profile/entries created at registration. It never
  deletes a program folder or edits a program row.
- No cascade. If a project still holds programs (excluding `_archive` and
  `_sandbox`), project unregister refuses and lists them.
- Archive mode: program → `Projects/<PROJECT>/_archive/…`; project →
  `<portfolio>/_archive/…` (create the portfolio archive only for a whole-project
  retirement, as the workspace rules allow). Write a small README in the archive
  with the date, original path and removed config entries.
- Hard delete uses `Remove-Item -LiteralPath` on the validated exact path only —
  never a wildcard or a recursive scan outside the target.
- **Never push `_archive` to git.** GitHub archiving is not a menu option and is
  not performed by these skills.
- Remove an MCP entry or profile only when no other entry still references it;
  if that cannot be proven, leave it and report. Never delete a stored credential
  automatically.
- Verify after every run: `memory_check.py --brief`, `registry_check.py --check
  --brief`, `specs_sync.py` (check), `closeout.py`, and `tools_now.py` for project
  removal. Report the exact paths removed, the chosen mode, and what remains.

## Co-edit contract — developer and agent on the same object

This contract applies to every program, classic or RAP. `program.yaml` carries
`kind`, `object_count` and `complexity`; the rest follows from that. The goal is
smooth handover, not a perfect mirror of SAP: the local files are a navigation
index, SAP remains the authority for versions and code diffs.

Three layers, never mixed:

| Layer | Where | Role |
|---|---|---|
| local index | `CHANGELOG.md` (all rows + `TR` + `Scope`), `spec/RAP_INDEX.md` for RAP | what changed, which TR, where to look |
| SAP authority | `SAPRead(VERSIONS/diff)`, `SAPTransport(list/get/history)`, `INACTIVE_OBJECTS` | current truth |
| decision gate | the user, via a question | resolve what neither layer can prove |

Start with `docs/coedit-capabilities.md`. A field absent from that matrix for the
active harness does not exist for this task: fall back to read-only or a human
gate. Never copy a capability from another harness — two installations can
disagree on whether a guard exists.

Three signal roles, never mixed:

| Role | Examples | Use for | Never use for |
|---|---|---|---|
| Hint | TR status/objectCount, `INACTIVE_OBJECTS`, `DEVC` anchor | choosing what to read | authorising a write |
| Evidence | `sourceHash`, `object_state.sha256`, diff, version | freshness and detection | claiming ownership |
| Guard | `expected_source_hash` + lock handle | preventing lost update | replacing user approval |

Hints and evidence are for navigation; only the guard makes a write safe, and
only the user resolves ambiguity. Anchor = UX, CAS = safety — not interchangeable.

Three cones, not one scope:

| Cone | Means | Gate |
|---|---|---|
| read-cone | objects we may read to understand a change | package allow-list does **not** gate reads |
| write-set | objects this task may change | package gate + `-AllowWrites`; one writer per object |
| data-cone | tables / CDS rows read for verification | `SAP_ALLOW_DATA_PREVIEW` / `SAP_ALLOW_FREE_SQL`, separate from writes |

A fact is either an **event** (released, cancelled, published, activated) written
once and never edited, or a **state** (draft present, publish state, anchor,
verified rows) that carries `source` (which tool), `by` (AI/human + harness),
`verified_at`, `verification_basis` (`source_hash` / `transport_snapshot` /
`user_attestation`), `confidence` (high/medium/low), and a TTL agreed in
`reports/DECISIONS.md`. TTL says how old the fact is, not that it is still true.
Without fresh state, re-probe — never inherit freshness from a previous session.

**Anchor** — `spec.md` front matter holds `last_tr_check` and `last_tr_seen`.
These are state: update them only after a live read, and treat them as stale when
their TTL has passed. A stale anchor is a reason to re-check, not a reason to
assume nothing changed.

**Hash store** — per-object observations live in `spec/coedit-state.json`, keyed by
`system/client/type/name/locator`. Keep `engine` beside every hash: an ai-dev
`sourceHash` and an ARC-1 `object_state.sha256` are computed differently and must
never be compared. A previous `object_state.sha256` is what makes an edit in an
open TR detectable (see the known limit below). Store the engine, locator, hash,
`checked_at` and TR together; delete the entry when the TR is released.

**Sync-on-touch** — before any task that writes or activates:

1. Read card + `spec.md` + newest CHANGELOG rows; for RAP also `RAP_INDEX.md`.
2. Cheap signals first. `SAPTransport(action="list", status="*", user="*",
   summary=true)` is one call and still reports `status` + `objectCount`, so a new
   TR, a release, or extra objects in an existing TR all show up. Add
   `SAPRead(type="INACTIVE_OBJECTS")` as a one-call "a draft exists" beacon.
3. For objects already in `spec/coedit-state.json`, add one
   `SAPDiagnose(action="object_state")` call each: `hasInactiveDivergence=true`
   means a draft is pending; an `active.sha256` different from the stored value
   means an external edit was activated even if the TR stayed open. Compare only
   hashes recorded by the same engine. A conditional-GET/ETag shortcut is
   deliberately absent — no mounted tool exposes it, so do not plan around it.
4. If those are silent but suspicion remains, check the package anchor
   (`SAPRead(type="DEVC", name=<package>, maxResults)`) before opening objects.
5. Light path (classic, `complexity: light`): no hit → continue with the local
   index; no further SAP read.
6. Heavy path (`kind: rap`, `object_count >= 20`, or `complexity: high`): start
   from the `spec/RAP_INDEX.md` sentinels — DDLS root, BDEF/behavior pool, DDLX,
   SRVD/SRVB publish state, draft — not a flat 120-object scan. Poll those first;
   when a fingerprint moves, expand one hop to immediate neighbours, run
   `SAPDiagnose(object_state)` on candidates, then `get` the TR, `diff` only the
   affected objects with `force_refresh=true`, and combine `impact` with
   `deps`/`usages`/`relations`. If only DDLS impact is available, mark the graph
   partial and do not use it to decide activation order.
7. Reconcile: show a short digest; ask the user before touching anything. Add one
   **new** CHANGELOG row with the TR and the affected `Scope`, `Verified:
   pending`; update only the affected `RAP_INDEX.md` rows and the anchor. Never
   rewrite or delete an old row, and never create a second log.

**Approval card — before the first edit.** For a task with more than a few steps,
keep the plan in `plan-<task>.md` (`templates/plan.md`) and show a short card in
chat: goal/acceptance, contract (FS, REQ ids, writer/verify/analyse, change type,
production, target + TR), write-set (type/name/locator/layer/hash engine/CAS),
activation units ordered bottom-up, checks (syntax/atc → commit window → mass
activate per unit → `force_refresh` read-back), and what we will **not** do
(SAP standard, publish, guessed TR, activation loop, rewriting an old CHANGELOG
row). Then ask **one** question with options `approve plan (Recommended)` /
`approve with a change` / `cancel`; never ask the user to type a magic word.
Approval is given once — only leaving the approved scope needs a new one. A
deploy pre-approved in the program card still stops on a finding.

**Activation gate** — before each activation run, not each object:

- Re-read the TR that will carry the work. One `question` call restates the TR,
  the object list and what remains; options `confirm` / `cancel`, default
  `cancel`. Execute only after `confirm`.
- Fast path: if the user named the TR in the handoff and `SAPTransport(history)`
  returns the same id, keep that as the candidate — but still ask the single
  confirm question. Otherwise use `list` + `get` to cross-check first.
- If the TR is released (`R`/`N`) or unclear, stop and ask. Never reuse a
  released TR; never invent a number.
- **Commit window** — after `confirm`, re-read every object in the write-set with
  `get_source(include_hash=true)` and re-check the TR before locking. A hash that
  no longer matches the plan drops that object: cancel the batch or split it and
  ask again. Do not carry a confirmed TR into a changed source.
- **Mass activation** — activate per **activation unit** with
  `ai-dev.activate_multiple(objects=[...])`, not object by object and not one
  blind batch for the whole program. Order objects bottom-up: includes before
  the main program; RAP = DDLS/tables → BDEF → behavior pool → projection/DDLX →
  SRVD/SRVB. A single `activate` can leave includes inactive or fail because a
  dependency's active version is not ready. If strict order matters and the
  tool's ordering is unverified, split into smaller per-layer batches. Parse the
  result per object: a partial failure stops the remaining units, reports
  diagnostics and does not retry in a loop. Mass activation does not bypass the
  commit window, CAS or TR confirmation; publish stays a separate boundary.
- A re-bound object gets a new CHANGELOG row with the new TR; the old row keeps
  the released TR.

**Handoff by recognition** — do not ask "did you edit anything?". Show an evidence
card per object (1–5): type/name, source locator, what moved (active/inactive
divergence or hash change), tool and time. Ask **attribution** first — "are these
yours?" with options `none of these` / `these are mine — which TR?` / `not sure`.
If claimed, ask for the TR and verify it with the probe. **Authorization** is a
separate question in the activation gate; never combine the two. `not sure` = stop.
Recognition of concrete objects beats recall of a vague edit.

Confidence decides whether to proceed: `high` = hash + active claim + matching
intent → offer continue, still confirm activation; `medium` = hash changed + TR
candidate → ask attribution; `low` = only a package/transport hint → no write.
Record `by` (`human|ai`) and `harness` from explicit human choice — SAP sees one
user and cannot distinguish harnesses. Every handoff appends a new block; never
edit an earlier one.

**Preemption** — the human can stop at safe points without freezing the session:
before adding an object to the write-set, before the first write, before
activate/publish, and whenever evidence changes, scope expands, CAS fails, a
lock conflicts, or the outcome is unknown. Stop only the affected write queue;
finish cleanup/unlock before pausing, then continue as a read-only observer and
offer reconciliation. Never ask "accept all" when more than five objects, mixed
classic/RAP, stale evidence, a no-CAS operation, or a publish/release boundary is
in play.

**Write protocol** — after the TR gate, before any edit. This guard exists in
ai-dev; ARC-1 `SAPWrite` is not mounted here, so do not claim the same guard on
`arc1-*`.

1. `get_source(include_hash=true)` → source + `sourceHash` **with the same engine
   that will write** (`ai-dev` here). For `CLAS`, select the include or method to
   narrow the write surface; store that locator beside the hash.
2. Lock the object in the confirmed TR.
3. Edit with `edit_source(expected_source_hash=<fresh hash>, ...)`; for tables
   `update_table` already requires the full `expected_source`. The field is
   optional in the schema — send it on every guarded write. If the hash no longer
   matches, stop and re-sync — never overwrite.
4. Unlock in a `finally` block, including on activation failure.
5. If the target include answers `404`, treat it as a create, not an edit — never
   auto-initialise it as a write.
6. Post-write read-back: `get_source(include_hash=true)` with the **same engine and
   locator** → resulting hash into `spec/coedit-state.json` (evidence detail goes
   to `reports/DECISIONS.md`, not `CHANGELOG.md`). If activate succeeded but the
   read fails, mark `committed_unverified` and block dependent writes.
7. Verify with `force_refresh=true` or a different engine: a read right after
   activation can be served from cache. Activated is not the same as observed.
   Never compare an ARC-1 hash with an ai-dev hash.

**Baseline and undo** — only the actual write-set gets a pre-image, never the
whole package or TR. After the fresh read and before the first write, store it
with `scripts/coedit_baseline.py save` (object key, locator, engine, intent, TR,
observed `source_hash`). After the post-write read-back, `attach` the resulting
hash to the same entry. Undo is a **write forward under CAS**, not a restore:

1. Re-read current source with the same engine and locator.
2. If current = post-hash → write the pre-image with `expected_source_hash=current`.
3. Otherwise three-way reconcile (`base` = post-image, `ours` = pre-image,
   `theirs` = current); overlapping hunks stop for human review.
4. Record the undo as a new event with `reverts_intent_id`; never rewrite history
   or restore on the strength of a TR/timestamp alone.

For RAP, group by activation unit (dependency / SCC) and undo only AI-written
objects in reverse topological order. Keep pre-images for the open TR plus 30–90
days after release, pin any incident blob, and keep `.baseline/` out of git.

**Error routing** — meanings differ, so routes differ:

| Result | Meaning | Route |
|---|---|---|
| `409` locked by another session | concurrency | stop and wait / ask; do not retry |
| `412` / hash mismatch | guard rejected the write | stop, re-read, replan; never overwrite |
| `423` not modifiable / no lock handle | TR or authorization | fix the TR or rights, not concurrency |
| `404` / `410` | object gone or renamed | record a tombstone; never silently recreate |
| `403` on a data call | data gate refused, not a write conflict | stop; never widen the gate or disable a guard |
| timeout / `5xx` | outcome may be unknown | read-after-timeout; zero replay until committed or not |

Error text is transport-level only: classify with the SAP error body and the
operation phase. Retry only an idempotent read with a known outcome and a still
valid hash — conflict never auto-retries.

**Read outcomes and gate outcomes — fail closed.** A check read has three answers:
`found` (value present), `none` (authoritatively absent) and `unreadable` (could not
look). `unreadable` is never coerced to "none" or an empty list. A gate verdict is
`pass` / `skip` / `advisory` / `block` / `unreadable`; a scan that could not run is
`UNAVAILABLE` and **fails** the gate — it is not a clean pass. Keep tool failure
(could not run) separate from verdict (found a problem); a blocked check names the
reason. No environment flag may widen the absolute prohibitions.

**Recheck budget / circuit breaker** — read once, reuse evidence, invalidate by
event. Re-probe on: dirty state, TR/activation change, ownership change, a
`409`/`412`/`423`/timeout, or a user statement that another harness edited the
object. Stop and ask when a locator's full source is read twice without a write
or invalidation, a dependency query repeats, CAS conflicts twice, activation
fails twice, or the plan is rebuilt twice. No empty recheck loop.

**Known limit — write it down, do not try to code around it:** if there is no
prior observation of the object, an edit made in SAP and activated while its TR
stays open leaves no source hash to compare and no local signal — the agent cannot
see it, and a wrong handshake answer stays wrong. Once a hash has been stored,
`SAPDiagnose(object_state)` can detect a later active-source change even with the
TR open; that is detection after a baseline, not reconstruction of history.
This is an information limit, not a bug — do not keep adding scans for the case
where no baseline exists.

## Source intake

An idea arrives from an external source, or a known source ships a new version:

1. Provenance row in `docs/source-catalogue.md` first — URL @ ref, version, date,
